# 0017. Customer accounts

**Date**: 2026-10-31
**Status**: In Progress

## Summary

Customers can now create an account with their name, phone, email, and a password, sign in, reset a forgotten password by email, and manage their details on a small `/account` page. Everything runs through Supabase Auth, which the shop already uses for the owner's sign in, and through Server Actions (server side form handlers), so no new service is added. Orders placed while signed in belong to the account, the checkout form fills itself from the profile, and the owner of an order can open and cancel it without the number plus phone lookup. Guests still order exactly as before, and the dashboard still needs the owner's authenticator code.

## Requirements

**User stories**:
- As a returning customer, I want to sign in once and have my name and phone filled in at checkout, so ordering again is quick.
- As a customer, I want my orders tied to my account, so I can open them without typing the order number and phone each time (and see them all in My Orders, feature 19).
- As a customer who forgot my password, I want a reset link by email, so I can get back in without calling the shop.
- As the owner, I want every new account to be a regular customer and the dashboard to stay mine alone.

**Acceptance criteria** (these build on spec 0012 for the shared field rules, spec 0015 for the order page access, and spec 0016 for the cancel action):

- **AC-1**: Sign in page. `/account/sign-in` follows `docs/design/pages/sign-in.md` (copy `sign-in.01` to `sign-in.22`, layout, components, accessibility): h1 per form, the login and register tabs (two 48px buttons with `aria-pressed`), the reset form without tabs, and the guest card ("المتابعة كضيف" to `routes.cart`, "تتبّع طلب" to `routes.orderTrack`). The first form comes from `?tab=login|register|reset` read on the server (anything else is `login`). After that the tab is client state in one `SignInTabs` component: switching changes the form without leaving the page, carries the typed email into the other form, and updates `?tab` with `history.replaceState` (no navigation, no server round trip). A tab button keeps focus; a link inside a form that switches it (AC-3, "نسيت كلمة المرور؟") moves focus to the new form's h1. An `error` value other than `link_expired` is ignored (`notice` belongs to `/account`, AC-9); the `link_expired` message shows until the reset form is submitted. The page is `noindex`, and the bottom bar's account tab is active. A visitor who is already signed in is redirected to `safeStorefrontNext(next)` at once.
- **AC-2**: Register. Fields in this order: "الاسم الكامل" (`personName(NAME_LIMITS)`, 2 to 80, `autoComplete="name"`), "رقم الهاتف" (`phoneField` from checkout, `type="tel"`, `dir="ltr"`, `autoComplete="tel"`), "البريد الإلكتروني" (`accountEmail`: trimmed, lowercased, a valid email, at most 254 characters, `type="email"`, `dir="ltr"`, `autoComplete="email"`), "كلمة المرور" (`newPassword`: at least 8 characters, counted as code points, and at most 72 bytes in UTF-8, counted with `TextEncoder`, since Supabase's hash stops at 72 bytes and an Arabic letter takes 2; no character class rules; `autoComplete="new-password"`; too long shows "كلمة المرور طويلة جداً."). A valid submit creates the Supabase Auth user with `full_name` in its metadata; the existing `handle_new_user()` trigger makes the `customer` profile with that name; the action then writes `profiles.phone` and `profiles.phone_e164` (`savePhoneAfterSignUp`: an update, and when it matches 0 rows, one `insert … on conflict (id) do update` of `full_name`, `phone`, `phone_e164`; a throw goes to AC-17). There is no email confirmation step: the visitor is signed in and redirected to `safeStorefrontNext(next)`.
- **AC-3**: Register refusals. An email that already has an account shows "هذا البريد مسجّل مسبقاً." with two link styled buttons, "تسجيل الدخول" and "نسيت كلمة المرور؟", that switch `SignInTabs` to the login or reset form with the typed email and `next` kept in component state (the email never goes into a URL). A password Supabase calls weak (too short or found in a known leak) shows "كلمة المرور ضعيفة أو ظهرت في تسريب سابق. اختر كلمة مرور أخرى." under the password field. A Supabase rate limit shows "محاولات كثيرة. حاول مرة أخرى بعد قليل." Any other Supabase error (`failed`) shows the generic "تعذّر إتمام العملية. حاول مرة أخرى." on every form. Field errors appear under their fields with `role="alert"` and focus moves to the first invalid one; an error with no field shows in an alert box above the button, which receives focus (`tabIndex={-1}`). A filled honeypot field (`HONEYPOT_FIELD`, hidden and `tabIndex={-1}` exactly as checkout's) creates nothing and shows the generic message. Typed values stay after any refusal, except passwords.
- **AC-4**: Roles. Every account this feature creates has role `customer`, whatever metadata is sent; no action in this feature writes `profiles.role` (it is only read, for `placed_by_role`). The roles are `customer`, `electrician`, and `admin`; all three are valid `actor_kind` values, and AC-13 maps `admin` to `customer`. Admin access does not change: `/admin` still needs role `admin` and `aal2` (spec 0001), so the owner signing in on the storefront (at `aal1`) can shop as themself, and the dashboard still asks for their code. A storefront sign in replaces the browser's session, so it ends an `aal2` dashboard session in that browser (the code is asked again). Supabase needs `aal2` to change the password of an account with an authenticator, so for the owner `setNewPassword` gets `insufficient_aal`, and `changePassword` returns the same code at once when `getAccountProfile().profile.role` is `admin`, before checking the current password (that check signs in again at `aal1` and would end the owner's dashboard session for nothing). Both show "لتغيير كلمة مرور حساب لوحة التحكم اتبع دليل الاستعادة." (the owner's path is `docs/runbooks/admin-mfa.md`, which gains a password section).
- **AC-5**: Sign in. Email and password ("كلمة المرور" with `autoComplete="current-password"`) sign the visitor in and redirect to `safeStorefrontNext(next)`. A wrong password and an unknown email both show "البريد الإلكتروني أو كلمة المرور غير صحيحة." A Supabase rate limit shows the too many message. Any other Supabase error (an outage, a network fault) is `failed` and shows the generic message, so an outage never reads as a wrong password. While pending, the button reads "جارٍ الدخول" and is disabled.
- **AC-6**: Where to go next. `safeStorefrontNext(next)` (pure, tested) percent decodes `next` once (a decode error means unsafe), then returns the original `next` only when it is at most 512 characters, starts with a single `/`, has no `//`, `\`, tab, or control characters in either form, and its path is not under `/admin`, `/auth`, or `/account/sign-in`; otherwise `routes.account`. A query and hash are kept (`/p/x?size=2` stays). The sign in page carries `next` from its query into the login and register forms as a hidden field, only when `safeStorefrontNext(next)` returns it unchanged; an unsafe `next` gets no field, so the default applies. The reset form carries no `next`.
- **AC-7**: Reset request. The reset form takes the email, calls `resetPasswordForEmail(email, { redirectTo: siteUrl + routes.auth.confirm })` (`siteUrl` from `src/lib/public-env.ts`), and always shows "أرسلنا رابط الاستعادة إلى بريدك." whether or not the email has an account. Every Supabase error here, rate limits and the per email resend throttle included, also shows that success message and is only logged, because the throttle fires only for real accounts and would reveal them. A filled honeypot sends nothing and shows the success message. The email is in Arabic, sent through Resend from the shop's domain in production, and links to `{{ .RedirectTo }}?token_hash=…&type=recovery`, so a preview deploy's links come back to that preview (its URL must be in the allowed redirect URLs).
- **AC-8**: Reset landing. `GET /auth/confirm` uses nothing up: it is a `noindex` page (h1 "استعادة كلمة المرور", the line "اضغط متابعة لتعيين كلمة مرور جديدة.", yellow large "متابعة") that holds `token_hash` and `type` in a form, so email scanners and link previews that open the link cannot burn the token. "متابعة" posts to `confirmRecovery`, which runs `verifyOtp({ type: "recovery", token_hash })` (this signs the visitor in) and redirects to `routes.accountResetPassword`. A missing token, a `type` other than `recovery`, or an expired or used token redirects to `/account/sign-in?tab=reset&error=link_expired`, where the reset form shows "انتهت صلاحية الرابط أو استُخدم من قبل. اطلب رابطاً جديداً." `/account/reset-password` (h1 "كلمة مرور جديدة") has "كلمة المرور الجديدة" and "تأكيد كلمة المرور الجديدة" (`new-password`, same rules as AC-2, must match: "كلمتا المرور غير متطابقتين.") and "حفظ كلمة المرور". Saving sets the password, ends every other session of the account (`signOut({ scope: "others" })`, so someone who took over the account is thrown out), and redirects to `/account?notice=password_set` ("تم تعيين كلمة المرور الجديدة."). Opening it while signed out redirects to `routes.signInWith({ next: routes.accountResetPassword })` (the login form). The page and `setNewPassword` work only within 10 minutes of the reset link: after a good token, `confirmRecovery` sets the `skf_recovery` cookie (httpOnly, SameSite Lax, Secure in production, path `/`, max age 600, value `<user id>.<seconds since the epoch>`), and the page (with the `getClaims()` `sub`) and the action (with the `getVerifiedUser()` id) accept it only when `isFreshRecovery(raw, userId, nowSeconds)` (pure and tested) finds the same user id and a stamp from 0 to 600 seconds ago. Saving a new password deletes the cookie, so one link sets one password; signing out (`signOutCustomer`) and a successful `changePassword` delete it too, so leaving the account ends the window. Confirming another link while it is set writes a new stamp. The session's `amr` claim cannot carry this: a recovery `verifyOtp` records method `otp`, the same as any other one time code (checked on local Supabase, 2026-10-31). Otherwise the page redirects to `routes.account`, where changing the password needs the current one (AC-10), and the action returns `recovery_expired`, shown as "انتهت مهلة رابط الاستعادة. اطلب رابطاً جديداً أو غيّر كلمة المرور من حسابي." So a signed in phone left unlocked cannot set a new password without the old one. `/auth/confirm` sends no referrer (`referrer: "no-referrer"` in its metadata), so the token in its address never leaves in a `Referer` header. A visitor who leaves without saving stays signed in with the old password, which is the same as signing in.
- **AC-9**: Account page. `/account` sends a signed out visitor to `/account/sign-in?next=/account`. Signed in, it shows h1 "حسابي", then three cards built from the existing Card, Field, Input, and Button parts: "بياناتي" (email read only, name and phone editable with the AC-2 rules, "حفظ التغييرات", success "تم حفظ بياناتك."), "تغيير كلمة المرور" (AC-10), and the outline "تسجيل الخروج" button. When the profile's `phone_e164` is null, a notice above the cards reads "أضف رقم هاتفك ليسهل علينا التواصل معك بخصوص طلباتك." A user with no profile row sees empty name and phone and the same notice; saving the profile form creates the row (the upsert in `updateProfileInDb`). The page is `noindex` and the account tab is active. On any account write form (profile, change password, new password), a session that ended before the submit (`not_signed_in`) shows "انتهت الجلسة. سجّل الدخول من جديد." in the alert box.
- **AC-10**: Change password. "كلمة المرور الحالية", "كلمة المرور الجديدة", "تأكيد كلمة المرور الجديدة", button "تغيير كلمة المرور". The current password is checked first (except for the owner, AC-4); a wrong one shows "كلمة المرور الحالية غير صحيحة." The new one follows AC-2's rules, must match its confirmation, and must differ from the current one ("كلمة المرور الجديدة مطابقة للحالية."). Success ends every other session of the account (`signOut({ scope: "others" })`), clears the fields, and shows "تم تغيير كلمة المرور."
- **AC-11**: Sign out. "تسجيل الخروج" ends this browser's session only (`signOut({ scope: "local" })`; the default would sign out every device) and redirects to `routes.home`; `/account` then redirects to sign in. The cart cookie and the `skf_placed` and `skf_tracked` cookies are left alone; `skf_recovery` is deleted (AC-8).
- **AC-12**: Bottom bar. The "حسابي" tab always links to `routes.account` (the shared layout never reads the session), and it is active on any `/account` path.
- **AC-13**: Checkout and order placement. For a signed in visitor, the checkout name and phone fields start with the profile's `full_name` and `phone` (empty when null) and stay editable; editing them never changes the profile. `placeOrder` reads the session at submit: signed in, the order gets `placed_by_user_id` = the user id and `placed_by_role` = the profile role at that moment, and its `created` event gets `actor_user_id` = the user id and `actor_kind` = that role, except that role `admin` is written as `actor_kind = customer` (a storefront order is a shopper's act, not a dashboard one; `placed_by_role` keeps `admin`). Signed out, a session that expired while the form was open, or a session with no profile row (logged as `order_profile_missing`), the order is a guest order exactly as today. `skf_placed` is still set either way. A replayed idempotency key returns the original order unchanged.
- **AC-14**: Order page for the owner. A signed in visitor whose user id equals the order's `placed_by_user_id` opens `/orders/<number>` with no cookie and no lookup. This check runs before the cookie check and before the admin redirect (spec 0015 AC-7). Anyone else, including another signed in customer, gets exactly today's behaviour.
- **AC-15**: Cancel by the owner. `cancelOrderByCustomer` also accepts an order whose `placed_by_user_id` equals the signed in user id, read with `getVerifiedUser()` (a write, so a revoked session is refused at once). It is called only when neither cookie holds the id, so guests and cookie holders pay no extra call. The rules, the guarded write, the WhatsApp hand off, and the recorded actor (`guest`) are those of spec 0016, unchanged.
- **AC-16**: Password and email settings. `supabase/config.toml` sets `minimum_password_length = 8` and an Arabic recovery template (`[auth.email.template.recovery]`, subject "استعادة كلمة المرور في S.K.F", `content_path = "./supabase/templates/recovery.html"`), and adds `http://localhost:8787/**` to `additional_redirect_urls` so reset links work under `pnpm preview`. Email confirmations stay off (`enable_confirmations = false`, already the local setting); with them on, `signUp` returns no session and AC-2 and AC-3 break. The production Supabase project matches: Confirm email off, minimum length 8, leaked password protection on, Resend SMTP, the recovery template, the auth email rate limit raised, and Site URL and redirect URLs set to the production address; these settings are listed in `docs/runbooks/supabase-production.md`.
- **AC-17**: Logging and partial failure. Each action logs one JSON line `{ event, ok, code }` (`code` only when refused; events `account_sign_up`, `account_sign_in`, `account_reset_requested`, `account_recovery_confirmed`, `account_password_set`, `account_password_changed`, `account_profile_saved`), never the email, name, phone, or password. A user id may appear (it is not contact data). If `signOut({ scope: "others" })` fails after a password set or change, the password stays changed and the action succeeds; `other_sessions_kept` is logged with the user id and the error code. If the phone write after sign up fails, the account stays, the visitor is still signed in and redirected, `profile_phone_save_failed` is logged with the user id, and AC-9's notice asks for the phone.
- **AC-18**: Tests. Vitest beside the source for the account schemas, `safeStorefrontNext`, the Supabase error to message mapping, and each action (signed out, refused, and success paths). Database tests for the phone write after sign up, the profile update, the owner read of an order, and the owner cancel. Playwright on a phone sized RTL screen (390) and a computer sized one (1280): register, land on `/account` with the name and phone shown; sign out; sign in with a wrong then the right password; register with a taken email; request a reset, open the link from the local mail catcher, set a new password, land on `/account`, sign in with it; change the password; check out signed in with the fields filled, see the order as a customer order in the dashboard, open its page from a new browser context signed in to the same account with no lookup, cancel it there; another account opening that page lands on the lookup. axe (`wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`) finds nothing on the sign in tabs, `/account`, and `/account/reset-password`; every control is at least 44 by 44; no sideways scroll.

## Decision

**Chosen option**: Option 1: Email and password accounts on Supabase Auth, handled by Server Actions in a new `accounts` feature.

Customers register with name, phone, email, and password, are signed in at once, and reset by an emailed link. Orders placed while signed in link to the account, which also opens and cancels those orders.

**Implementation skills**: `supabase` (`supabase/agent-skills`, `.agents/skills/supabase/`, Auth with `@supabase/ssr`, the confirm route, auth settings) · `vercel-react-best-practices` (`vercel-labs/agent-skills`, `.agents/skills/vercel-react-best-practices/`, Server Actions and `useActionState` forms) · `shadcn` (`shadcn-ui/ui`, `.agents/skills/shadcn/`, Tabs, Card, Field on Base UI) · `playwright-cli` (`microsoft/playwright-cli`, `.agents/skills/playwright-cli/`)

**Calls made in this spec** (each with the runner up; reasons in `rationale.md`):
- Server Actions call the server Supabase client (`createSupabaseServerClient`), the same as the admin sign in. Runner up: the browser Supabase client.
- Reset links use the `token_hash` template and `verifyOtp` in `/auth/confirm`, so the link works when opened on a different device. Runner up: the PKCE `code` link.
- The current password is checked with `signInWithPassword` before `updateUser`. Runner up: Supabase's reauthentication code by email.
- Account writes (profile, passwords) call `getVerifiedUser()`; reads (prefill, order page, placement) use `getClaims()`. Runner up: `getClaims()` everywhere.
- The pages that show the account's own details (`/account`, `/account/orders`, `/account/reset-password`, and the electrician's `/account/drafts` and `/account/quick-order` through `requireElectricianPage`) and the sign in page's signed in check also call `getVerifiedUser()` (`getVerifiedAccount()` for `/account`), so a session ended by a reset elsewhere (AC-8) is signed out on its next page, not when its token expires up to an hour later. The sign in page must match them, or a revoked session bounces between the two. Found by `/check verify` on 2026-11-04.
- A new password without the current one is allowed only within 10 minutes of a reset link, checked through the httpOnly `skf_recovery` cookie that `confirmRecovery` sets, bound to the user id (updated 2026-10-31: the first pick, the session's `amr` claim with method `recovery`, does not exist, since Supabase records a recovery as `otp`). Runner up: an `amr` entry with method `otp` at most 600 seconds old (signed, so it cannot be forged, but this spec would then rely on Supabase never adding another `otp` path to a customer account).
- The honeypot sits on register and reset only, the two forms that create something or send an email. Runner up: on all three forms.
- The code lives in `src/features/accounts/`, and the admin sign in stays in `admin-auth`. Runner up: one shared `auth` feature.

## Feature design

**Data model sketch**: no new table, column, enum value, or migration. Spec 0002 as built:

| Table | Columns this feature uses | How |
|---|---|---|
| `auth.users` (Supabase owns it) | `id`, `email`, `raw_user_meta_data.full_name` | created by `signUp`; email shown on `/account` from the session claims |
| `profiles` | `id` PK FK `auth.users` cascade; `full_name`; `phone`; `phone_e164` (indexed, **not** unique); `role` | row made by the trigger (role `customer`, name from metadata); phone written by `registerCustomer`; name and phone edited by `updateProfile`; role only read |
| `orders` | `placed_by_user_id` (nullable FK `profiles` set null); `placed_by_role` (nullable) | set by `placeOrder` when signed in; read by the owner checks (AC-14, AC-15) |
| `order_events` | `actor_user_id`, `actor_kind` on `created` | set by `placeOrder` when signed in |

Relationships: `auth.users` 1 to 1 `profiles`; `profiles` 1 to many `orders` (guest orders have none).

**State transitions**: none new. A visitor is either signed out or signed in (a Supabase session in cookies); `/auth/confirm` signs in through a reset link. Order status rules stay as specs 0014 and 0016.

Step order inside `registerCustomer`: honeypot, then Zod, then `supabase.auth.signUp({ email, password, options: { data: { full_name } } })`, then `savePhoneAfterSignUp` (a `getDb()` update of the profile row the trigger made; zero rows falls back to the upsert; a throw logs AC-17 and continues). `signUp` reports network faults as a returned error, not a throw, so they map to `failed`, then the log line, then the redirect. `changePassword`: `getVerifiedUser()`, Zod, `signInWithPassword({ email: user.email, password: current })` (an `invalid_credentials` there becomes `wrong_current`), then `updateUser({ password })`. Supabase checks length and leaks on `signUp` and `updateUser` and rejects with `weak_password`; the Zod rule only catches short ones early.

**Order page and cancel wiring**: in `customer-order.ts`, a new `readOwnedOrderId(db, orderNumber, userId): Promise<string | null>` selects `orders.id` by number where `placed_by_user_id = userId`. `getCustomerOrder(orderNumber)` first reads `getClaims()`; with a user and an owned id, it calls the existing `readCustomerOrder(db, orderNumber, [ownedId])`. Otherwise it continues with the `skf_placed` / `skf_tracked` ids exactly as today, and the page's admin redirect stays after both. No cookie is set for an owner visit. `cancelOrderByCustomer` passes its check when the id is in either cookie **or** `isOwnedOrder(db, orderId, user.id)` (one `select 1 from orders where id = $1 and placed_by_user_id = $2`, with `user` from `getVerifiedUser()`, asked only when neither cookie holds the id) is true; then it calls `cancelOrderByCustomerInDb` with the same id as today.

**Key invariants**:
- No action in this feature writes `profiles.role`; a new profile is always `customer`.
- `profiles.phone_e164` is always `normalizePhone(phone)` or null; both columns change together.
- An order's `placed_by_user_id` is set only at placement and only from the verified session's `sub`, never from form input.
- Editing checkout fields never writes to `profiles`; editing the profile never changes saved orders.
- The order page and cancel open an order only through one of: the owner's session, `skf_placed`, `skf_tracked`.
- Passwords never reach a log, a database column of ours, or a redirect URL.

**Security model**: All actions are public POST endpoints, so each validates with Zod on the server, and Next.js refuses cross site POSTs (Origin check). Supabase Auth stores and hashes passwords, issues the sessions, and rate limits sign up, sign in, and auth emails per IP; the honeypot drops simple bots on register and reset. Writes to an account (profile, passwords) use `getVerifiedUser()`, so a revoked session is refused at once; reads use `getClaims()`. The owner checks compare `placed_by_user_id` with the session's `sub`, so one customer can never open another's order. All data goes through `getDb()` in `server/` modules with `server-only`; RLS and the revoked grants keep `profiles` and `orders` closed to `anon` and `authenticated`. The `next` value is limited to storefront paths (no open redirect). Registering with a taken email says so (accepted: low risk for a shop). A new password without the current one needs a reset link opened in the last 10 minutes (AC-8), proven by the httpOnly `skf_recovery` cookie; page scripts cannot read or set it, and it only counts for the user id it was set for. Login CSRF through a reset link is accepted: someone can send you their own link and you would land in their account, which holds nothing of yours; `/auth/confirm` sends no referrer so the token does not leak. Emails, names, and phones are personal data and fall under the project's no logging rule. No regulated compliance scope applies. The dashboard guard (`requireAdmin()`, role `admin` + `aal2`) is unchanged.

**Configuration required**: no new env var or secret. `NEXT_PUBLIC_SITE_URL` already exists. Supabase settings (AC-16): `minimum_password_length = 8`, the recovery template, and in production leaked password protection, Resend SMTP, a raised email rate limit, Site URL, and redirect URLs. Prerequisite for resets in production: the Resend sending domain is verified (spec 0001 follow-up).

**Critical test scenarios**:
- Happy path: register on a phone, land on `/account`, check out with the fields filled, and the dashboard shows a customer order with the user id, verifies **AC-2**, **AC-9**, **AC-13**
- Happy path: reset through the local mail catcher (port 54324) and sign in with the new password, verifies **AC-7**, **AC-8**
- Failure case: taken email, weak password, wrong password, used reset link, and the phone write failing after sign up (account kept, notice shown), verifies **AC-3**, **AC-5**, **AC-8**, **AC-17**
- Auth/permission: another signed in customer opening or cancelling the order lands on the lookup or gets `not_found`; a signed up account opening `/admin` is sent to the admin sign in; a `next` of `//evil.example` or `/admin` lands on `/account`, verifies **AC-4**, **AC-6**, **AC-14**, **AC-15**

## Consequences

**Positive**:
- No new vendor: sign in, sessions, hashing, rate limits, and reset emails come from Supabase Auth, which the owner sign in already runs on.
- Orders gain an owner, which My Orders (19), roles (20), electrician drafts (21), and loyalty (31) all need.
- Shared field rules mean the profile name and phone always pass checkout's checks.

**Negative / tradeoffs**:
- No email confirmation: a mistyped email can never receive a reset link, and until feature 20 only a database edit fixes it. Someone could also register with another person's email (the real owner can take it back with a reset).
- Phones are not verified and not unique, so the phone on a profile proves nothing about who owns it.
- The register form reveals whether an email already has an account.
- Orders a customer placed as a guest before registering stay outside the account; My Orders will not show them.
- A cancel by a signed in owner is still recorded as `guest`, so the dashboard history cannot yet say which account cancelled.
- Checking the current password with `signInWithPassword` issues a fresh session and counts against the sign in rate limit.
- Sessions last until sign out, so a customer who stays signed in on a shared phone shares their account.
- The owner cannot change or reset their password from the storefront (Supabase needs the authenticator for it); they follow the runbook. Signing in on the storefront ends their dashboard code session in that browser.
- A reset link takes one extra tap ("متابعة"), the price of surviving email scanners.
- The `skf_recovery` cookie is not signed (the project has no signing secret, and this spec adds none). Someone at an unlocked, signed in computer who opens the browser's developer tools and knows the cookie format could fake it and set a new password without the old one. It still stops the casual case on a phone, where editing cookies is not practical.
- Google sign in, planned in spec 0001, is not offered.

**Neutral**:
- `/account` and `/account/reset-password` are not in the design package; they are built from existing parts and need the owner's look in a real browser.
- The checkout page and the order page now read the session; both were already dynamic.
- The account forms submit from the browser (`startTransition` after `preventDefault`), so they need JavaScript to work; the `/auth/confirm` button is a plain form and does not.
- `/account/orders` stays missing until feature 19, which also becomes the default after sign in and the account tab's target.
