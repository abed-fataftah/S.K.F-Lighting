# 0020. Electrician quick order and drafts

**Date**: 2026-11-03
**Status**: In Progress

## Summary

Electricians get a quick order page where every order is a named draft (for example "ali / mo") saved on the server as they type. They add up to 30 lines by typing a product name or code in each line, choose the size and colour, and enter a quantity; prices fill in live and the total updates. A card on the same page holds the end customer's name, phone, and delivery details. Sending checks everything, creates a normal order owned by the electrician (through the same order insert as checkout), deletes the draft, and opens the usual WhatsApp page. Two new tables (`drafts`, `draft_lines`) hold the work in progress; nothing else in the order model changes.

## Requirements

**User stories**:

- As an electrician, I want to build a large order line by line without opening product pages, so I can price a whole job in minutes.
- As an electrician, I want to keep several named drafts, one per end customer, and come back to any of them from my phone or computer, so nothing I typed is lost.
- As an electrician, I want the order to carry my end customer's name, phone, and address, so the shop delivers to them.
- As an electrician, I want a clear block when a line has no quantity or a price changed, so I never send something I did not mean.
- As the owner, I want electrician orders to arrive like any other order, typed كهربائي, with the electrician named in the WhatsApp message.

**Acceptance criteria** (these build on spec 0002 for the model, spec 0004 and 0012 for placing an order, spec 0010 for search, spec 0013 for the WhatsApp message, spec 0017 for accounts, spec 0019 for roles, and `docs/design/pages/quick-order.md` and `docs/design/pages/drafts.md` for layout and copy):

- **AC-1**: Electricians only. `/account/quick-order` and `/account/drafts` are storefront pages with `noindex`. Each page reads `getAccountProfile()` (role fresh from the database on every request, spec 0001). Signed out: redirect to `routes.signInWith({ next })` with the current path. Signed in but not allowed (no profile row, role `customer` or `admin`, or `removalPending`): redirect to `routes.account`. Every draft Server Action and the search endpoint (AC-7) make the same check first and return `forbidden` (the endpoint: 401 signed out, 403 not allowed); on `forbidden` the page navigates to `routes.account`. Nothing about drafts is shown to anyone else.
- **AC-2**: Entry. On `/account`, when the role is `electrician`, a card "أدوات الكهربائي" sits under the "حساب كهربائي" badge (spec 0019 AC-9) with two buttons: "طلب سريع" (`routes.quickOrder`) and "مسوداتي" (`routes.drafts`). Customers and the owner see nothing new. The bottom bar's حسابي tab is active on both new pages.
- **AC-3**: Drafts list. `/account/drafts` shows an h1 "مسوداتي", a yellow small button "+ مسودة جديدة" (`routes.quickOrder`), and the line "احفظ طلباتك لكل زبون باسم خاص، وعُد إليها في أي وقت." Then one card per draft owned by the user, sorted by `updated_at` newest first, then `id` descending. Each card: the name (16/800), a muted line "{count} · آخر تعديل {date}" where count is the number of all its lines, written with the project's plural pattern (`{count, plural, zero {لا أسطر} one {سطر واحد} two {سطران} few {{shown} أسطر} many {{shown} سطرًا} other {{shown} سطر}}`, with `shown` passed as `formatNumber(count)`, as in `ar.json` `count`) and date is `updated_at` through `formatDate` in the shop time zone; a yellow "فتح" button (`routes.quickOrderDraft(id)`) and an outline trash icon button with `aria-label` "حذف المسودة {name}" (AC-15). With no drafts, the empty card "لا توجد مسودات" with the yellow "+ مسودة جديدة" button. At most 30 drafts exist (AC-4), so there is no paging.
- **AC-4**: A new draft. `/account/quick-order` with no `draft` param shows the h1 "طلب سريع", the line "للكهربائيين: أضف حتى 30 سطراً في طلب واحد.", and the name card: the field "اسم المسودة" focused on load, the hint "اكتب اسم المسودة للبدء", and the outline buttons "فتح مسودة" (`routes.drafts`) and "مسودة جديدة" (`routes.quickOrder`). The lines, customer, and totals sections are not rendered yet. Pressing Enter in the name field, or leaving it with text in it, calls `createDraft({ name })`. The name is tidied (spec 0005 `tidyText`, single line) and must be 2 to 40 characters; it must differ from every other draft of the user, comparing Latin letters case insensitively (`lower(name)`; Arabic text is compared after `tidyText` only, with no letter folding). The unique index is the final judge: a `23505` on it maps to `name_taken`, so two racing creates cannot both win. Success creates the draft with one empty line and replaces the address with `routes.quickOrderDraft(id)` (no new history entry). Errors under the field: "اكتب اسماً من حرفين على الأقل." (`invalid`, too short or empty), "الاسم أطول من 40 حرفاً." (`invalid`, too long), "لديك مسودة بهذا الاسم." (`name_taken`), "وصلت إلى 30 مسودة. أرسل مسودة أو احذفها لتبدأ أخرى." (`too_many_drafts`). A `draft` param that is not a uuid, or names a draft that does not exist or belongs to someone else, redirects to `routes.drafts` (a sent draft no longer exists, so an old link lands there too).
- **AC-5**: Rename. On a draft page the name card shows the draft's name in the same field. Editing it autosaves through `renameDraft({ draftId, name })` by the text rule of AC-12, with the same rules and messages as AC-4; renaming a draft to its own name with different Latin case is allowed (the clash check excludes the draft itself). A refused name stays in the field with its error and is not saved; the last saved name stays in the database.
- **AC-6**: Lines. Under the h2 "الأسطر" and the counter "{n} / 30" (`formatNumber`), each line is a card and a `fieldset` whose `legend` is "السطر {position}" (position 1, 2, 3… by `sort`, renumbered on screen after a removal). It holds: the product combobox "الكود أو اسم المنتج" (AC-7); the selects "الحجم" and "اللون"; the quantity field "الكمية"; a footer with the unit price and the line total; and a trash icon button 44 by 44 with `aria-label` "حذف السطر {position}". A select is shown only when the chosen product's options (`archived_at is null`) carry that dimension; it lists the distinct values in option `sort` order, and "اللون" lists only colours that exist with the chosen size. When exactly one option matches what is chosen (including a product with a single option), it becomes the line's option. The pure `resolveOption(options, size, colour)` settles the edge cases: a product whose only option has no size and no colour shows no selects and is chosen at once; when some options carry a dimension and others do not, the missing value is a choice "بدون حجم" or "بدون لون"; when the product has sizes, "اللون" stays disabled until a size is chosen; changing the size clears a colour that does not exist with the new size; with two or more matches nothing is chosen yet. An option that is not sellable shows in the select as "{value} (غير متوفر)" and is disabled. A line that already holds an archived or unsellable option keeps it and shows the AC-14 badge; for a product that cannot be sold at all, the selects are read only. Footer: "سعر الوحدة: {price}" once an option is chosen; "من {lowest}" when only the product is chosen and its option prices differ; the line total is `price × quantity` through `formatPrice` when both are set, else "—".
- **AC-7**: Product search. Typing in a line's combobox calls `GET routes.api.quickOrderProducts(q)` (`/api/quick-order/products?q=`) 250 ms after typing stops, cancelling any older request. `q` follows spec 0010 AC-2 (`readSearchRequest`); under 2 folded characters nothing is fetched. It returns up to 8 products matching and ordered exactly as spec 0010 AC-3 and AC-4 (listed products only, every word as a substring of `search_text`, then the code tier, in stock first, `created_at desc`, `id desc`). Each product carries its options with `archived_at is null` in `sort` order (id, code, size label, colour name, price, sellable), at most 40 per product, and `exactOptionId` when the code query equals one option's code (when the code equals both a product code and an option code, the option wins). The route sits outside `/api/catalog/`, so `src/proxy.ts` refreshes the session for it and the handler reads the role through `getAccountProfile()`. No rate limit: it needs an electrician account and is debounced. Each suggestion row shows a 40 px thumbnail (first product image, or the placeholder), the name, the product code, and the price ("من {lowest}" when option prices differ). Choosing a row sets the product on the line; when `exactOptionId` is set, choosing it sets that option too. No match: one muted row "لا توجد نتائج". A failed request, or one slower than 3 seconds (the catalog's `withTimeLimit`): one row "تعذّر البحث. حاول مرة أخرى." The response has `Cache-Control: private, no-store`. Built on the shadcn Combobox for Base UI (combobox ARIA, keyboard, RTL).
- **AC-8**: Saving a line. Choosing a product calls `updateDraftLine({ lineId, productId, variantId })`, with `variantId` the option resolved by AC-6 (or `exactOptionId`) or null; changing the product clears the option and keeps the quantity; choosing the product the line already has changes nothing. Product and option are written together: any refusal leaves both as they were. The server refuses with `invalid` an option that is archived or does not belong to the product (an unsellable but not archived option may be saved and shows the badge). A `23505` on the line's unique index maps to `duplicate`, with a second read for the other line's position. Choosing a size or colour that resolves to an option saves it the same way. The quantity saves when the field is left or Enter is pressed: Arabic digits count; empty saves null; digits clamp to 1 to 999; anything else returns to the last saved value. Choosing an option that is already on another line of this draft is refused with `duplicate` and the other line's position: the line keeps its previous choice, and the line shows "هذا الخيار موجود في السطر {n}" with a link button "انتقل إلى السطر {n}" that moves focus to that line's quantity. A line whose product is set but option is not, or whose quantity is null, is incomplete.
- **AC-9**: Adding and removing lines. The outline large button "+ إضافة سطر" calls `addDraftLine({ draftId })`, which appends an empty line (`sort` one past the highest) and moves focus to its product field. At 30 lines the button is disabled and the counter reads "30 / 30"; the server refuses a 31st with `too_many_lines`. The trash button calls `removeDraftLine({ lineId })`; the line disappears and a toast "تم حذف السطر {position}" offers "تراجع" for 5 seconds, which calls `restoreDraftLine({ draftId, productId, variantId, quantity, sort })` and puts the line back in its place (lines always order by `sort`, then `created_at`, then `id`, so a repeated `sort` still has a stable place; a line whose product became unavailable meanwhile comes back with the AC-14 badge). A restore refused with `duplicate` or `too_many_lines` shows the toast "تعذّر إرجاع السطر." Removing every line is allowed; the page then shows only the add button.
- **AC-10**: End customer card. Between the lines and the totals, a card "بيانات الزبون" holds the checkout fields with the checkout labels (spec 0012): name, phone, pickup or delivery, and for delivery the zone (active zones, `readActiveZones`), city, and address; then notes. An outline small button "الطلب لي" copies the user's `profiles.full_name` and `profiles.phone` into name and phone (still editable) and saves them; it is disabled when the profile has no phone. A new draft has neither pickup nor delivery chosen. A saved zone that is no longer active shows in the select as "{zone} (غير متاحة)" and is refused at send with `zone_invalid`; a deleted zone becomes empty (`on delete set null`). Each field autosaves through `saveDraftCustomer({ draftId, ...fields })` by AC-12's rules. While drafting, values are only tidied and cut to the checkout maximums (name 80, city 60, address 300, notes 500, phone 30); `customer_phone_e164` is `normalizePhone(phone)` or null. Choosing pickup keeps any saved zone, city, and address (so switching back restores them), and they are ignored on send. Full checks run only on send (AC-13).
- **AC-11**: Totals. The totals card shows "المجموع", the sum of `price × quantity` over complete lines that are sellable; "التوصيل" with the zone fee (shown as checkout shows it) only when delivery and an active zone are chosen; and "الإجمالي" (18/800) = المجموع + التوصيل. When some lines are incomplete or not sellable, a muted line sits under the total, "{n} لا تدخل في الإجمالي" with n written by the same plural pattern as AC-3 (سطر واحد, سطران, {shown} أسطر, {shown} سطرًا). Every figure goes through `formatPrice`. The page recomputes with the pure `draftTotals` after every save, from the live prices the read and each line action return.
- **AC-12**: Autosave. In place of the design's "حفظ كمسودة" button, the totals card has a `role="status"` line: "جارٍ الحفظ…" while a save runs, "تم الحفظ" after, "تعذّر الحفظ" with an outline button "إعادة المحاولة" after a failure. Timing: product, size, colour, pickup or delivery, and zone save at once; quantity on leave or Enter (AC-8); text fields 800 ms after typing stops and on leave. Saves run one at a time in the order made, through one client queue per draft: several pending edits of the same field collapse into the latest value; a server reply (`DraftLineView`) replaces a line on the page only when no newer edit for that line is waiting; a new line shows as pending (not editable) until `addDraftLine` returns its id; removing a line drops its queued edits. A failed save keeps the typed value on the page, retries by itself on the browser's `online` event (network failures only; a refusal such as `invalid` is shown, not retried), and blocks send (AC-13). While any change is unsaved or a save is running, leaving the page asks first (`beforeunload`). When the page becomes visible again, nothing is pending, no field has unsaved text, and no field or combobox has focus, it reloads the draft from the server (`router.refresh()`). A save answered `not_found` (the line or draft is gone, for example deleted on another device) reloads the page; if the draft itself is gone, the page goes to `routes.drafts`. When the same draft is edited on two devices, the last save of each field wins.
- **AC-13**: Send. The green large button "إرسال الطلب عبر واتساب" first waits for running saves; if any save failed it shows "احفظ التغييرات أولاً." and stops. Then the page checks every line and the customer card, marking each problem inline (`aria-invalid` and `aria-describedby`): a line with no product "اختر منتجاً لهذا السطر.", no option "اختر الخيار لهذا السطر.", no quantity "أدخل الكمية لهذا السطر."; customer fields with the checkout messages (spec 0012). Focus moves to the first problem. If all pass it calls `sendDraft({ draftId, expectedTotal })`, `expectedTotal` being the الإجمالي shown. The server, in order: `getVerifiedUser()` and the AC-1 role check (`forbidden`); the order rate limit `orderRateCheck()` (`rate_limited`); if an order has `idempotency_key = draftId` **and** `placed_by_user_id` = the user, it answers `replayed` with that order (an order with that key placed by anyone else is `not_found`, so a guessed or shared draft id never reveals or unlocks another person's order). Then, in one transaction: lock the draft `for update` with the owner check (missing: the same owner scoped replay lookup again, `replayed` if found, else `not_found`); no lines `empty`; any incomplete line `incomplete`, returning each line's position and reason (`no_product`, `no_option`, `no_quantity`) so the page marks them even when its own check passed; customer fields parsed with `checkoutSchema` from a raw object built from the draft (`name` and `phone` the stored text as typed, `fulfilment`, `zoneId`, `city`, `address`, `notes`; every null becomes `""` so it reports `required`, a null fulfilment is reported as `required` on the fulfilment field; `idempotencyKey` the draft id; `expectedTotal` the action input), `invalid` with field errors shown through checkout's own error message map; the order row uses the schema's parsed and tidied output, never the stored strings; any line not sellable `not_sellable`; delivery with a zone that is not active `zone_invalid`; the computed total (spec 0004 rules, live prices, the zone fee) not equal to `expectedTotal` `price_changed`. Otherwise it writes the order through the shared order insert (spec 0004 placeOrder steps 6 and 7, also used by checkout): `placed_by_user_id` the user, `placed_by_role` `electrician`, the customer fields from the draft, order lines in draft line order with copied names and prices, a `created` event with actor `electrician`; then deletes the draft (its lines go by cascade), and commits. The order of checks is fixed, so a draft with both an incomplete and an unsellable line answers `incomplete`. The page's الإجمالي equals the server's total only when every line is complete and sellable, which is exactly when send gets this far. On `placed` or `replayed` the action calls `rememberPlacedOrder(orderId, { clearCart: false })` (the electrician's storefront cart is not touched; checkout keeps clearing it) and redirects to `routes.checkoutDone(number)` with `?wa=1`, the same W5 page as checkout. Success is that redirect; every failure is a returned result. Refusals show a notice banner at the top of the totals card: `price_changed` "تغيّرت بعض الأسعار. راجع الإجمالي ثم أرسل مرة أخرى." and the page reloads the draft so the new prices show; `not_sellable` "بعض الأسطر غير متوفرة. احذفها أو استبدلها ثم أرسل."; `zone_invalid` "منطقة التوصيل لم تعد متاحة. اختر منطقة أخرى."; `empty` "أضف سطراً واحداً على الأقل."; `rate_limited` the checkout's message; `incomplete` and `invalid` mark the fields as above; anything else "تعذّر إرسال الطلب. حاول مرة أخرى."
- **AC-14**: Lines that cannot be sold. A line whose product or option fails `isSellable` (product not active or unavailable, category not shown, option unavailable or archived) shows a badge "غير متوفر", no unit price and no line total, is left out of the totals (AC-11), and blocks send (AC-13). The electrician removes it or picks another option.
- **AC-15**: Delete a draft. From each drafts list card, and from an outline small button "حذف المسودة" in the quick order name card, an `AlertDialog` titled "حذف المسودة «{name}»؟" with the text "ستُحذف أسطرها وبيانات الزبون. لا يمكن التراجع." and the buttons "حذف" (danger) and "تراجع". Confirm calls `deleteDraft({ draftId })`. Success shows the toast "تم حذف المسودة." and lands on, or refreshes, `routes.drafts`. `not_found` (already gone) is treated as success.
- **AC-16**: WhatsApp line. When the order's `placed_by_role` is `electrician`, the W5 message (spec 0013) gains one line right after the title: "الكهربائي: {name}" (`OrderMessage.electrician`), the name being the placing account's `profiles.full_name`, joined in `readPlacedOrder` (`src/features/checkout/server/queries.ts`) when `placed_by_role = 'electrician'`. When that name is null (or the account is gone) the line is left out. Other orders' messages do not change; the spec 0013 message tests gain the electrician cases.
- **AC-17**: A product on a draft is archived, not deleted. Spec 0006's product delete counts a `draft_lines` row for the product as a use, like an order line: the product is archived and the draft line stays, showing "غير متوفر" (AC-14).
- **AC-18**: Role changes. Drafts are never deleted by a role change (spec 0019 AC-7 needs no change). While an account is a customer its drafts are unreachable (AC-1); promoted again, the same drafts are back. Removing an account (spec 0019 AC-11) deletes its drafts with the profile through the cascade.
- **AC-19**: Logs. One JSON line per event: `draft_created`, `draft_deleted`, `draft_sent` with `orderNumber`, `lineCount`, `total`, `draft_refused` with `error` (and field names for `invalid`), `draft_save_failed` with the action name and error name, and `quick_order_search_failed` with the error name. Never a draft name, a customer field, a search text, or an id of a person.
- **AC-20**: Layout and access. Both pages follow their design pages at 390. At wider screens they use the design's interim: the phone layout in one centered column of `--page-max` (480 px). Only design tokens, logical properties, and the format helpers are used (the design and language rule tests pass). Every control is at least 44 by 44; labels are real `label` elements; errors are tied with `aria-describedby`; no sideways scroll at 390.
- **AC-21**: Tests. Vitest beside the source for the draft name and customer schemas, `commitDraftQuantity`, `resolveOption` (AC-6), `draftTotals` and the incomplete count, `lineProblems` (AC-13), the send outcome mapping, the WhatsApp electrician line, and the new routes. Database tests for `createDraftInDb` (name rules, case insensitive clash, the 30 draft limit under two concurrent creates), the line writes (`duplicate`, `too_many_lines` under concurrency, restore in place, `updated_at` bumped, `not_found` on someone else's line), `saveDraftCustomerInDb`, `readDraft` with live prices and sellability, the search read (order, 8 limit, `exactOptionId`, unlisted products absent), `sendDraftInDb` (each refusal, `incomplete` reasons, a null fulfilment as `required`, success writes the order from the parsed input, lines in order, the event, and deletes the draft; a replay and two concurrent sends make one order; a second electrician sending the first one's draft id gets `not_found`, never the order), `rememberPlacedOrder` with `clearCart: false` keeping the cart cookie, `writeOrder` with checkout's existing tests still passing, the product delete archiving a product that is only on a draft, and the migration checks. Playwright on 390 and 1280 as an electrician: create a draft, build 30 lines by search with no product page opened, see the 31st refused, leave a quantity empty and see send blocked, fill it, reload and see everything kept, fill the customer card with delivery, send, land on the W5 page with the electrician line, and see the order typed كهربائي in My Orders; the drafts list (open, delete with the dialog); a customer and a signed out visitor redirected. axe (`wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`) finds nothing on both pages, the combobox open, and the delete dialog.

## Decision

**Chosen option**: every quick order is a named server draft, autosaved one field at a time through small Server Actions, with a per line product combobox fed by a GET search endpoint, sent through the checkout's shared order insert inside one transaction that also deletes the draft.

Draft tables follow spec 0002 with four changes recorded below (nullable product and option on a line, a 1 to 999 quantity, no `area`, no `submitted_*` columns). The order model, status flow, and the done page stay as they are.

## Feature design

**Data model sketch** (one migration, schema file `src/server/db/schema/drafts.ts`, exported from the schema index; both tables `.enableRLS()` with no grants to `anon` or `authenticated`):

`drafts`
| Column | Type | Rules |
|---|---|---|
| `id` | uuid | PK, default `gen_random_uuid()`; becomes the order's `idempotency_key` on send |
| `owner_user_id` | uuid | not null, FK `profiles` on delete cascade |
| `name` | text | not null, `check (char_length(name) between 2 and 40)` |
| `customer_name` | text | nullable |
| `customer_phone` | text | nullable, as typed |
| `customer_phone_e164` | text | nullable |
| `fulfilment` | `fulfilment_method` | nullable |
| `delivery_zone_id` | uuid | nullable, FK `delivery_zones` on delete set null |
| `city`, `address`, `notes` | text | nullable |
| `created_at` | timestamptz | not null, default now() |
| `updated_at` | timestamptz | not null, default now(); set to now() by every draft and line write |

Indexes: unique `(owner_user_id, lower(name))`; `(owner_user_id, updated_at desc, id desc)` for the list.

`draft_lines`
| Column | Type | Rules |
|---|---|---|
| `id` | uuid | PK |
| `draft_id` | uuid | not null, FK `drafts` on delete cascade, indexed |
| `product_id` | uuid | nullable, FK `products` on delete restrict, indexed (AC-17 reads it) |
| `variant_id` | uuid | nullable; composite FK `(variant_id, product_id)` to `product_variants (id, product_id)` on delete restrict |
| `quantity` | integer | nullable, `check (quantity between 1 and 999)` |
| `sort` | integer | not null |
| `created_at` | timestamptz | not null, default now() |

Checks: `variant_id is null or product_id is not null` (the composite FK is not checked when one part is null). Unique `(draft_id, variant_id)`; Postgres treats nulls as distinct, so several empty or product only lines are fine.

Relationships: `profiles` 1:N `drafts`; `drafts` 1:N `draft_lines`; `products` 1:N `draft_lines`; `product_variants` 1:N `draft_lines`. No price is stored; lines always read the live `product_variants.price`.

**State transitions**: a draft has no status column. It is created (AC-4), edited any number of times (AC-5 to AC-12), then either sent, which creates an `orders` row in status `new` and deletes the draft in the same transaction (AC-13), or deleted (AC-15). A line is empty, product only, or complete (option and quantity); sellability is computed at read time, never stored.

**API surface** (Server Actions in `src/features/drafts/server/actions.ts`, each returning `Result<T, E>`; database halves in `src/features/drafts/server/*.ts` with `server-only`, through `getDb()`):

| Endpoint | Method | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| `createDraft` | Server Action | `name: string` | `{ draftId }` | electrician (`getClaims` path via `getAccountProfile`) | `forbidden`, `invalid`, `name_taken`, `too_many_drafts` |
| `renameDraft` | Server Action | `draftId: uuid`, `name` | `{ name }` | electrician, owner | `forbidden`, `invalid`, `name_taken`, `not_found` |

Page reads (server, `server-only`): `readMyDrafts(db, userId)` for the list (id, name, line count, `updated_at`); `readDraft(db, userId, draftId)` returning the draft, its lines in `(sort, created_at, id)` order, and the active zones. It is a new query, not `readCartRows` (which starts from the option and inner joins, so it would drop product only lines): it starts from `draft_lines`, left joins `products` on `product_id` and `product_variants` on `variant_id`, joins the category and its main and `colours` like `readCartRows`, and adds each product's non archived options for the selects. Archived products, hidden categories, and archived options still come back (name, code, labels) with `sellable = false` from `isSellable`.

Every ownership check joins `drafts.owner_user_id = userId` in the same statement as the read or write, so another user's id reads as `not_found`. Line writes lock the parent draft `for update`, count lines, check duplicates, write, and set `drafts.updated_at = now()` in one transaction. `createDraft` locks the user's `profiles` row `for update` before counting drafts, so two concurrent creates cannot pass 30.

**Key invariants**:
- A draft is visible to, and changed by, only its owner, and only while the owner is an electrician without a pending removal.
- At most 30 drafts per owner and 30 lines per draft, enforced under a row lock.
- One line per option within a draft (unique `(draft_id, variant_id)`).
- A draft line never stores a price; every shown or ordered price is the live price at that moment, and an order is only written when its total equals the total the electrician saw.
- One draft makes at most one order: the order's `idempotency_key` is the draft id, and the draft is deleted in the same transaction that writes the order.
- A replay only ever returns an order the caller placed; sending never touches the storefront cart.
- Lines always order by `(sort, created_at, id)`, on the page, in the list count, and in the order's lines.
- An order from a draft has only complete, sellable lines and customer fields that pass `checkoutSchema`, exactly like a checkout order.
- Draft data never reaches logs.

**Security model**: All data goes through Drizzle in `server/` modules; the browser never queries the database. Both tables have RLS enabled with no policies and no grants, checked by `pnpm db:check-rls`. Reads use `getClaims()` through `getAccountProfile()`; `sendDraft` calls `getVerifiedUser()` first because it creates an order (the AGENTS.md rule for money changes). Every action and the search endpoint check the electrician role themselves, not only the page. Ownership is a `where owner_user_id = sub` in the same statement, so another user's ids are `not_found` and never confirm existence. Inputs are parsed with the shared Zod schemas on the server. Drafts hold personal data (end customer names, phones, addresses, and draft names that are often a person's name): they are never logged, are deleted on send, and go with the account on removal. The search endpoint returns only what the storefront already shows publicly. Send is rate limited like checkout; draft edits are bounded by the 30 by 30 limits and need an electrician account, so they get no separate limit. No regulated compliance scope applies.

**Configuration required**: none. The existing `ORDER_RATE_LIMITER` binding is reused.

- Happy path: an electrician creates "ali / mo", adds 30 lines by search with quantities, fills the customer card with delivery, sends, and lands on W5 with the electrician line; the order has 30 lines in order, `placed_by_role` `electrician`, and the draft is gone. - Failure case: a price changes after the page loaded; send is refused with `price_changed`, nothing is written, the page shows the new price; a second send succeeds. Two concurrent sends of the same draft make exactly one order. Verifies **AC-11**, **AC-13**
- Failure case: a quantity is left empty and an option goes unavailable; send is blocked with both lines marked. Verifies **AC-8**, **AC-13**, **AC-14**

## Consequences

**Positive**:
- Work is never lost: every change is on the server within a second, and a draft follows the electrician between phone and computer.
- One order path: drafts and checkout share the same insert, numbering, event, and done page, so dashboard, My Orders, and WhatsApp need almost no change.
- Sending is safe to retry and safe against two taps or two devices, through the draft id key, the row lock, and the price check.
- No personal data lingers: a sent draft is deleted, and account removal takes drafts with it.

**Negative / tradeoffs**:
- Autosave means many small writes (one per field change); fine for a few electricians, but each costs a Worker request and a Hyperdrive round trip.
- Server Actions run one at a time per page, so a slow save delays the next; on a weak connection the status line will show "جارٍ الحفظ…" often.
- Last save wins across two devices can quietly overwrite a field edited elsewhere; accepted because one electrician rarely edits one draft in two places at once.
- Half filled lines in the database need nullable columns and an extra check, and every reader must handle the three line states.
- A product that sits only on a draft can no longer be hard deleted; it is archived instead.
- The 480 px column at desktop is narrow for a 30 line order; a real desktop layout waits for design (O-1).

**Neutral**:
- The spec 0002 sketch of `drafts` changes: no `area`, `submitted_order_id`, or `submitted_at`; `draft_lines` gains `product_id` and nullable `variant_id`, and quantity runs to 999.
- The design's "حفظ كمسودة" button becomes a save status line, and the design gains a customer card it did not draw.
- A new UI kit part (Combobox) arrives, usable by later features.
- `writeOrder` becomes the single place orders are inserted; returns and payments features will meet it.
